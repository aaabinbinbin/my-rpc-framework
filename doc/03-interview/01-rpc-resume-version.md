## 3. 项目简介模板

### 3.1 极简版

> 从零实现并持续重构 RPC 框架，完成服务注册与发现、动态代理调用、统一协议编解码、Netty/Socket 双传输切换、SPI（可插拔扩展点）扩展机制，以及限流、熔断、降级、重试等治理能力，并支持 Spring Boot（应用启动框架）自动接入。

### 3.2 标准版

> 自主设计并重构一套 RPC 框架，基于 ZooKeeper 实现服务注册与订阅发现，基于 JDK/CGLIB 动态代理完成远程调用封装，支持 Netty/Socket 双传输、统一协议编解码、SPI 扩展式序列化器与负载均衡器，以及 consumer/provider 双侧限流、熔断、降级和重试能力，同时支持 Spring / Spring Boot 注解驱动接入。

### 3.3 强调重构版

> 将一个早期功能可用但结构较散的 RPC 项目重构为分层清晰的框架骨架，完成配置系统分层、服务发现目录缓存、调用编排链、统一协议层、Netty/Socket 双传输、SPI 扩展机制、双侧治理能力及 Spring Boot 接入，显著提升可读性、可扩展性与接入体验。

## 4. 项目亮点条目模板

下面这些内容适合放在简历项目经历的 bullet（要点条目）里，你可以挑 4 到 6 条。

### 4.1 架构与分层

- 对 RPC 框架进行骨架级重构，将项目拆分为配置层、bootstrap（启动器）层、调用编排层、服务发现层、协议层、传输层、治理层和 Spring 接入层，明确各层职责边界。

### 4.2 服务注册与发现

- 基于 ZooKeeper 实现服务注册与订阅发现，设计本地 `ServiceDirectory` 目录缓存，支持地址快照、预热、TTL（生存时间）和 stale fallback（旧快照回退），避免每次请求直接访问注册中心。

### 4.3 动态代理与调用编排

- 基于 JDK 动态代理与 CGLIB 实现服务代理，封装 `RpcRequest/RpcResponse` 模型，并引入方法级配置解析、Filter（过滤器）链和 Cluster（集群容错）策略，形成完整 consumer（消费端）调用编排链路。

### 4.4 传输层

- 实现 Netty 与 Socket 两套传输层，支持按配置切换 transport（传输实现）；其中 Netty 版支持连接池、请求管理、心跳与断线重连，Socket 版作为最小实现与对照测试路径。

### 4.5 协议层

- 设计统一协议头与消息模型，将 `magicNumber/version/messageType/serializerType/requestId` 收口到 `RpcHeader`，实现统一协议编解码，支持多序列化器切换。

### 4.6 SPI 扩展

- 设计轻量 SPI 扩展机制，支持按名称加载和缓存序列化器、负载均衡器与 Filter，实现 `protobuf/json/kryo/java/hessian` 等序列化器和 `random/roundRobin` 等负载均衡器的配置化切换。

### 4.7 容错治理

- 实现 consumer/provider 双侧治理能力，包括请求级重试、服务级/方法级熔断、限流、降级与失败转移，并支持方法级配置覆盖治理策略。

### 4.8 Spring 接入

- 实现 `rpc-spring` 与 `rpc-spring-boot-starter`，支持 `@RpcService`、`@RpcReference` 注解驱动接入，以及 `rpc.*` 配置绑定和自动装配，降低框架使用成本。

### 4.9 工程化能力

- 梳理项目包结构与文档体系，补齐调用链、配置系统、SPI 扩展、协议层、传输层和治理层专题文档，提升项目可读性和后续演进效率。

## 7. 简历里少写但面试时要能展开的内容

下面这些内容不一定全写在简历上，但你要准备在面试里展开：

1. 为什么 transport（传输层）要和 invocation（调用编排层）分层
2. 为什么服务发现要做目录缓存
3. 为什么同时保留 Netty 和 Socket
4. 为什么治理能力通过 Filter 链接入
5. 为什么要做 Spring Boot starter（启动器）

也就是说，简历负责“钩住问题”，面试再负责展开。

---

## 8. 小结

简历里这类项目最重要的不是写得多，而是写得准。

这类项目最建议突出三件事：

1. 这是一个真正有骨架的 RPC 框架，不是单一 demo（演示）
2. 你做了重构和分层，不是只堆功能
3. 你把核心链路、治理能力和工程接入都补到比较完整的程度
