# RPC 项目面试与展示材料

## 1. 这份材料怎么用

这份文档不是给你继续看源码用的，而是给你在下面这些场景直接使用的：

1. 简历项目描述
2. 面试里的项目介绍
3. 面试官追问时的展开回答
4. 自己整理“这个项目到底做了什么”的表达模板

它重点解决两个问题：

1. 怎么把这个项目讲清楚
2. 怎么把你在这个项目里的改造价值讲出来

---

## 5. 面试中的 3 分钟介绍

如果面试官愿意多听一点，可以讲这版：

> 我这个项目本质上是一个从零实现并持续重构的 RPC 框架。最开始它能完成基本远程调用，但问题是结构比较乱，比如 transport、配置、代理、治理逻辑耦合得比较紧，后面一加功能就容易越改越散。  
> 后来我重点做了一轮骨架级重构。首先在架构上，把项目拆成了配置层、bootstrap 层、调用编排层、注册发现层、协议层、传输层、SPI 扩展层、治理层和 Spring 接入层，这样不同职责就有了明确落点。  
> 在功能上，我把完整主链路补齐了：消费端通过动态代理把本地调用封装成 `RpcRequest`，再经过方法级配置解析、Filter 链、服务发现目录、负载均衡和 cluster 策略后交给 Netty 或 Socket 发送；服务端收到请求后，通过统一协议解码、dispatcher、provider Filter、业务线程池和本地注册表完成反射调用，再返回 `RpcResponse`。  
> 在运行时能力上，我补了 ZooKeeper 订阅发现、本地目录缓存、consumer/provider 双侧限流、consumer 熔断和降级、provider 降级、请求级重试、连接级重连、心跳、优雅停机，以及 SPI 扩展式序列化器和负载均衡器。  
> 在接入体验上，我又把框架接进了 Spring 和 Spring Boot，支持 `@RpcService`、`@RpcReference` 和 `rpc.*` 配置绑定。现在这个项目的重点不是对标成熟框架的生态完整度，而是已经把骨架、主链路和扩展能力搭起来了，后续继续优化会容易很多。

## 6. 最值得讲的点

如果面试官问：

> 你觉得这个项目里最有价值的部分是什么？

可以从下面几项里挑 2 到 4 项讲。

### 6.1 我做的不是功能堆叠，而是结构重构

这个点很重要。  
很多学生项目的问题不是功能少，而是：

1. 所有逻辑混在一起
2. 没有清晰层次
3. 扩展点不明确

你这个项目最大的价值之一，就是做了完整骨架收口。

可用回答：

> 这个项目里我做得最重要的一件事，不是简单加几个功能，而是把框架结构拆清楚了。我把配置、bootstrap、调用编排、服务发现、协议、传输、治理和 Spring 接入这些层都整理出来了，这样后面新增功能时就不会继续污染主链路。

### 6.2 我明确区分了服务发现、负载均衡、cluster 和 transport

这很能体现你对 RPC 调用链的理解。

可用回答：

> 我在项目里刻意把一次 RPC 调用拆成多个阶段：服务发现负责拿地址列表，负载均衡负责选实例，cluster 决定失败后是否重试或失败转移，transport 只负责真正发请求。这样每层职责都很清楚。

### 6.3 我做了 consumer/provider 双侧治理

可用回答：

> 我后面补了治理能力，而且不是只做单侧。consumer 侧有方法级限流、熔断、降级和重试，provider 侧有方法级限流、降级和业务线程池隔离，这样两端的保护能力比较完整。

### 6.4 我做了 SPI 扩展机制

可用回答：

> 我把序列化器、负载均衡器和 Filter 都收成了 SPI 扩展点，通过配置按名字切换，而不是在主链路里写一堆 if/else。这样主链路不会因为支持更多实现而继续膨胀。

### 6.5 我把它接进了 Spring Boot

可用回答：

> 我后面把框架接进了 Spring 和 Spring Boot，支持 `@RpcService`、`@RpcReference` 和 `rpc.*` 配置绑定。这让它不只是一个纯核心 demo，而是更接近真实 Java 项目里的接入方式。

## 7. 项目亮点总结版

如果面试官问：

> 你这个项目的亮点是什么？

可以概括成下面 5 点：

1. 完整 RPC 主链路：注册发现、代理调用、协议编解码、客户端/服务端收发、响应返回
2. 清晰架构分层：配置、bootstrap、invoke、discovery、registry、protocol、transport、resilience、spring
3. 双传输实现：Netty 和 Socket 可按配置切换，证明上层编排和底层收发已解耦
4. 双侧治理能力：consumer/provider 两侧都有保护能力
5. 工程化接入：支持 Spring / Spring Boot 自动注入与配置绑定

## 8. 你做过哪些关键重构

这个问题非常容易被问到。  
可以按这些点讲：

### 8.1 配置系统分层重构

原来：

1. 配置读取和配置绑定混在一起
2. `RpcConfigLoader` 过大

后来：

1. 拆成 `RpcPropertySource`
2. 拆成多个 binder
3. Boot 场景下单独引入配置适配层

### 8.2 服务注册和服务发现分层

原来：

1. 注册和发现容易混在一层

后来：

1. 拆出 `ServiceDiscovery`
2. 引入 `ServiceDirectory`
3. 支持本地缓存、预热和 fallback

### 8.3 transport 选择下沉到工厂层

原来：

1. Netty 还是 Socket 的选择不够统一

后来：

1. 引入 transport/server 工厂
2. bootstrap 和 proxy 都能按配置切换 transport

### 8.4 静态全局状态收口

原来：

1. 代理工厂有静态全局 client 主路径

后来：

1. 改成实例工厂为主
2. 静态入口只保留兼容能力

### 8.5 Filter 与运行态治理解耦

原来：

1. `FilterManager` 同时承担 Filter 解析和运行态治理配置

后来：

1. `FilterManager` 只负责 Filter 装配
2. `FilterRuntimeConfigurator` 负责治理初始化

## 9. 高频追问

下面这些问题是高概率会被追问的。

### 9.1 为什么同时保留 Netty 和 Socket

推荐回答：

> 我保留 Socket 不是为了和 Netty 重复造轮子，而是为了保留一个最小 transport 对照实现。这样更能证明上层调用编排、服务发现、负载均衡和治理逻辑已经和底层收发解耦了。Netty 更适合完整功能，Socket 更适合理解最小实现和做对照测试。

### 9.2 为什么不把重试直接放在 transport 里

推荐回答：

> 因为重试是请求级治理决策，不是连接级问题。transport 只应该负责收发和连接管理，而重试需要结合方法级配置、异常语义和 cluster 策略来决定，所以我把它放在 invocation/cluster 层而不是 transport 层。

### 9.3 为什么需要 RpcContext

推荐回答：

> 因为 traceId、requestId、attachments 这些信息本质上是调用上下文，不适合散在每层方法参数里。用 `RpcContext` 之后，Filter、日志和调用编排都能共享这份上下文，主链路会更干净。

### 9.4 为什么注册和发现要拆开

推荐回答：

> 注册中心层更偏基础设施，负责注册、下线和 watcher；服务发现层更偏 consumer 视角，负责目录缓存、快照、预热和 fallback。拆开后 consumer 请求路径不需要每次都直接打注册中心。

### 9.5 为什么要做 Spring Boot 接入

推荐回答：

> 因为如果项目只停留在纯 Java 手工 bootstrap，那更像 demo。接进 Spring 和 Spring Boot 后，业务方可以直接用 `@RpcService`、`@RpcReference` 和 `rpc.*` 配置来使用，接入体验更自然，也更接近真实 Java 项目。

## 10. 如果问和 Dubbo / gRPC 的差距

推荐回答不要硬比成熟度，而是诚实但有层次。

> 我这个项目和 Dubbo、gRPC 这类成熟框架最大的差距，不在某一个点，而在工程成熟度和生态完整度。比如它们在协议演进、性能优化、治理能力、配置中心、监控链路、生态集成上都会更完整。  
> 但我这个项目的重点不是直接对标成熟框架的完成度，而是参考它们的设计思路，把一个原来比较散的自研 RPC 项目收成有清晰骨架、可扩展、可继续演进的框架形态。从这个目标看，我现在已经把核心结构和主链路搭起来了。

---

## 11. 如果问这个项目最能体现你什么能力

推荐回答：

> 我觉得最能体现的，是架构收口和系统性重构能力。因为写一个 Netty 客户端或者写一个 ZooKeeper 注册不是最难的，真正更难的是知道什么逻辑该放在哪一层、哪些能力该抽成扩展点、哪些配置该统一收口，以及怎么让一个原来比较散的项目变成后面还可以继续长的结构。

## 15. 小结

这份材料的核心作用是：

把“你做了很多东西”变成“你能清楚讲出你做了什么、为什么这么做、价值在哪里”。

对这个项目来说，真正能打动面试官的不是你写了多少类，而是：

1. 你知道 RPC 框架应该怎么分层
2. 你能解释每一层为什么这么设计
3. 你能说明自己做的是结构化改造，而不是功能堆叠
