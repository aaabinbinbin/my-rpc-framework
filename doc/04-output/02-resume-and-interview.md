# 简历与面试：怎么把这个项目讲得稳、具体、能经得住追问

## 1. 为什么“会看项目”和“会讲项目”完全不是一回事

很多人花了很多时间看项目，最后却在两个场景里掉链子：

1. 写简历时写不出有区分度的项目描述
2. 面试时介绍项目时总觉得自己讲得散、讲得虚、讲着讲着就乱

这不是因为你没看懂，而是因为“输出形式”本身也是一项单独能力。

尤其是框架类项目，它和普通业务项目相比，更容易出现两个问题：

### 问题一：讲得太技术，听的人抓不到主线

一上来就是：

- Netty
- ZooKeeper
- 动态代理
- SPI
- 熔断限流
- Spring Boot Starter

这些词都没错，但如果没有主线，听起来像工具清单。

### 问题二：讲得太泛，听的人又觉得你不具体

比如：

`我做了一个 RPC 框架，实现了远程调用。`

这句话方向没错，但信息太少，别人很难判断你到底理解到什么程度。

所以真正成熟的表达要同时满足两件事：

1. 有主线
2. 有细节支撑

这篇就是专门解决这个问题的。

---

## 2. 先把简历表达和面试表达彻底分开

这是第一步，也是很多人最容易混的地方。

### 简历表达的目标

简历不是为了完整教学，而是为了：

1. 让面试官快速知道你做了什么项目
2. 让面试官知道这个项目有一定技术深度
3. 让面试官愿意基于这个项目继续追问你

所以简历需要的是：

`压缩过的信息密度。`

### 面试表达的目标

面试不是为了压缩到极致，而是为了让别人相信：

1. 这个项目你真的做过 / 理解过
2. 你不是只会背几个关键词
3. 你能顺着主线展开，也能接住细节追问

所以面试需要的是：

`有结构的展开能力。`

一句话区分：

- 简历：压缩表达
- 面试：展开表达

你如果不先把这件事分开，后面很容易把简历写得像长文，把面试讲得像关键词列表。

## 3. 简历里最常见的 5 个错误

先把错误看清楚，后面正确写法才更有对比。

### 错误 1：只写技术名词，不写主线

例如：

```text
使用 Netty、ZooKeeper、SPI、Spring Boot Starter 实现了 RPC 框架。
```

问题：

别人依然不知道你到底实现了什么核心链路。

### 错误 2：只写一句很空的话

例如：

```text
实现了一个 RPC 框架项目。
```

问题：

过于空泛，没有任何区分度。

### 错误 3：把模块名写成项目成果

例如：

```text
项目包含 rpc-core、rpc-spring、starter、example-consumer、example-provider。
```

问题：

这只是目录结构，不是项目价值。

### 错误 4：写太细，像源码导读

例如：

在简历里直接写：

- `RpcInvocationHandler`
- `RpcRequestDispatcher`
- `RpcClientInvocationExecutor`

问题：

简历不是源码阅读笔记，写太细会降低可读性。

### 错误 5：把治理能力写成杂项清单

例如：

```text
支持重试、熔断、限流、降级、SPI、序列化、负载均衡、Starter……
```

问题：

看起来“很多”，但没有层次。

---

## 4. 一条最稳的简历表达公式

对于这个项目，简历里最稳的表达公式可以压缩成：

```text
项目类型
+ 核心主链路
+ 关键增强能力
```

套到当前项目里，就是：

### 第一步：点明项目类型

`基于 Java 实现自研 RPC 框架。`

### 第二步：点明你打通了什么主链路

例如：

`完成 consumer 代理调用、请求对象化、服务注册发现、Netty 通信、provider 本地执行链等核心能力。`

### 第三步：点明有哪些增强能力

例如：

`并实现 Spring / Spring Boot 集成、可插拔序列化与负载均衡扩展，以及基础重试、限流、熔断和降级设计。`

把这三步合起来，就是一条比较成熟的简历项目描述。

---

## 5. 一版可直接用的简历项目描述

下面是一版适合直接写进简历的项目描述：

```text
基于 Java 实现了一个自研 RPC 框架，围绕 consumer 代理调用、请求对象化、服务注册发现、Netty 请求响应通信和 provider 本地执行链打通远程调用闭环；在此基础上实现了 Spring / Spring Boot 集成、方法级配置、可插拔序列化与负载均衡扩展，以及基础重试、限流、熔断和降级能力。
```

这版的优点：

1. 先点明项目类型
2. 再点明主链路
3. 最后点明增强能力
4. 没有陷入类名堆砌
5. 也没有空到只剩一句“实现 RPC 框架”

这是一版比较平衡的写法。

---

## 6. 如果你想把简历写得更像“自己做了什么”，可以拆成多条 bullet

有些场景里，一段总述不够，还想拆出更清晰的成果点。那可以拆成 3 到 4 条。

例如：

```text
- 基于 Java 自研 RPC 框架，打通 consumer 接口代理调用到 provider 本地服务执行的完整闭环。
- 实现基于 Spring / Spring Boot 的接入方式，支持通过 @RpcReference 和 @RpcService 完成 consumer 注入与 provider 服务发布。
- 设计 RPC 协议头、请求响应消息模型及 Netty 通信流程，完成请求编码、解码、连接复用与异步响应匹配。
- 引入方法级配置、SPI 扩展机制及基础治理能力，支持序列化器、负载均衡器切换，以及重试、限流、熔断和降级。`
```

这种写法更适合：

- 你的简历项目栏允许多条描述
- 你想让面试官一眼就能看见“主链路 + 接入 + 通信 + 治理”四块能力

## 7. 简历里哪些内容最好不要写得太细

下面这些内容，通常不建议在简历里直接展开到源码级：

1. 类名清单
2. 每个 handler 名字
3. 每个协议头字段
4. 每个 filter 的实现细节
5. 每个 SPI 扩展的内部机制

原因很简单：

简历不是让别人一次看完你的全部理解，而是让别人愿意继续问你。

所以简历最好的状态不是“已经把一切说完”，而是：

`既准确又留有追问空间。`

## 8. 面试时“介绍一下这个项目”，最稳的开场怎么讲

这几乎是一定会遇到的问题。

最稳的开场，不要一上来就讲模块，也不要先报技术栈。

推荐顺序是：

1. 项目目标
2. 最小闭环
3. 主链路
4. 分层结构
5. 增强能力
6. 自己的理解

下面给你一版适合 1 到 2 分钟的开场答案：

```text
这个项目是一个自研 RPC 框架，目标是让 consumer 端以接近本地调用的方式访问 provider 提供的远程服务。项目最小闭环是：consumer 端通过接口发起调用，框架先通过代理把方法调用转成 RpcRequest，再经过服务发现、负载均衡、集群策略和 Netty 传输把请求发到 provider；provider 收到请求后根据消息类型分流，再通过本地注册表定位到具体服务实现执行，最后把结果封装成 RpcResponse 返回。

在结构上，我把核心能力放在 rpc-core，把 Spring 容器生命周期对接放在 rpc-spring，把 Boot 自动装配上移到 starter，同时把契约层和示例应用拆成独立模块。除此之外，项目还补充了方法级配置、SPI 扩展、可插拔序列化和负载均衡，以及基础重试、限流、熔断和降级能力。

我自己觉得这个项目比较核心的价值，不是只把 HelloService 这种 demo 跑通，而是把整个调用链按代理、编排、协议、传输和 provider 执行做了比较清晰的分层，这样后续扩展和排查会更容易。`
```

这版的特点是：

- 不空
- 不散
- 不会一上来就太底层
- 能自然承接后续追问

## 9. 面试时真正要练的，不是“背答案”，而是“主线稳定”

很多人准备面试时容易变成机械背诵。

这样有两个问题：

1. 一旦面试官打断，你就乱了
2. 一旦追问换个角度，你就接不上

所以更有效的做法是：

`把一条最稳定的主线练熟。`

对于这个项目，这条最稳定的主线就是：

```text
consumer 业务调用
-> 代理接管
-> RpcRequest 构造
-> 调用编排
-> 服务发现 / 负载均衡 / 容错
-> Netty 发送
-> provider 分流
-> 本地注册表定位服务
-> 执行业务方法
-> RpcResponse 返回
```

只要这条主线你能稳定讲清楚，后面无论是追问：

- Spring
- 协议
- SPI
- 配置
- 限流熔断

你都能把它们重新挂回这条主线上。

这才是最稳的应对方式。

## 10. 面试时常见追问会集中在哪几类问题

这一部分很重要。因为“会介绍项目”和“会接住追问”仍然不是一回事。

### 第一类：主链路追问

这类问题最常见，通常是为了判断你是不是只会背概述。

可能会问：

1. consumer 端是怎么把本地调用变成远程调用的？
2. provider 端收到请求后怎么找到本地实现类？
3. 为什么 consumer 注入的是代理对象而不是实现类？
4. provider 为什么还需要本地注册表？

这类问题的关键不是记术语，而是要顺着链路说。

### 第二类：设计取舍追问

这类问题是为了判断你有没有结构理解。

可能会问：

1. 为什么要拆 `rpc-core` 和 `rpc-spring`？
2. 为什么协议和传输要分开？
3. 为什么代理层不直接负责所有调用逻辑？
4. 为什么要有 `RpcClientInvocationExecutor` 这种编排类？

这类题的回答重点是：

`职责拆分、边界清晰、便于扩展、避免大而全类。`

### 第三类：扩展和治理追问

这类问题是为了判断你是不是真的理解“主链路之外的能力是怎么挂进去的”。

可能会问：

1. 负载均衡器怎么切换？
2. 序列化器怎么切换？
3. 方法级配置怎么生效？
4. 重试、限流、熔断分别适合放在哪一层？

这类题的关键是：

- 不要只答“支持”
- 要答“它插在链路的哪一步”

### 第四类：源码入口追问

这类问题通常会比较细。

可能会问：

1. 你觉得最关键的几个类是哪几个？
2. 如果要读源码，你建议先看哪几个类？
3. 一次 `helloService.sayHello()` 你会怎么追源码？

这类题如果你前面 `03-source-reading` 那一组文档已经吃透，通常不难接。

## 11. 每一类追问，分别应该怎么接

为了让你更容易练习，这里把常见追问的回答方向直接给出来。

### 11.1 问：consumer 端怎么把本地调用变成远程调用？

可以这样答：

```text
consumer 端业务代码里通过 @RpcReference 注入的是代理对象，这个代理对象由 RpcProxyFactory 创建，实际调用由 RpcInvocationHandler 接管。业务代码调用接口方法时，RpcInvocationHandler 会把服务名、方法名、参数类型、参数值和返回值类型组装成 RpcRequest，再交给调用执行器继续处理。`
```

### 11.2 问：provider 端怎么找到本地实现类？

可以这样答：

```text
provider 启动时会通过 RpcProviderBootstrap 把服务接口和实现对象注册到本地注册表。请求到达 provider 后，RpcRequestDispatcher 会先分流业务请求，再由下游执行链根据 serviceName 从本地注册表里查到对应的服务对象，例如 HelloServiceImpl，然后再通过方法名和参数类型完成本地方法调用。`
```

### 11.3 问：为什么要把协议和传输拆开？

可以这样答：

```text
协议层解决的是消息长什么样，比如头字段、消息类型、序列化方式和编解码顺序；传输层解决的是消息怎么发，比如连接、发送、接收、超时和连接复用。把两者拆开以后，更容易替换网络实现或者调整消息格式，也避免把所有细节都混进 Netty 代码里。`
```

### 11.4 问：为什么要有调用执行器，而不是代理直接发请求？

可以这样答：

```text
因为代理层只适合负责入口接管和请求对象化，真正一次调用还涉及方法级配置、限流、过滤器、负载均衡、集群策略和重试。如果把这些都塞进代理层，代理类会变得很重。单独抽出 RpcClientInvocationExecutor 作为编排中心，职责会更清晰，也更便于扩展。`
```

这几类回答你如果能练顺，面试时稳定性会明显提高。

## 12. 面试里什么时候该说类名，什么时候不该说

这是一个很实际的问题。

### 适合说类名的时候

1. 面试官已经开始追源码
2. 你在解释一条具体链路
3. 你想证明自己确实读过实现

例如：

- `@RpcReference` 是在 `RpcSpringManager` 里注入的
- 代理真正的入口是 `RpcInvocationHandler`
- 调用编排在 `RpcClientInvocationExecutor`
- provider 入口分流在 `RpcRequestDispatcher`

### 不适合一上来就说类名的时候

1. 刚开始整体介绍项目
2. 面试官还没建立项目图景
3. 你只是想先把项目是什么讲清楚

因为一开始类名太多，听者反而更难抓住主线。

所以建议：

- 开场先讲“系统级表达”
- 追问后再逐步落到类级表达

这会更自然。

## 13. 如果面试官追问“你自己觉得这个项目最核心的价值是什么”，怎么答

这是很容易拉开差距的问题。

比较差的答法是：

`我觉得学到了很多技术。`

这种答法太虚。

更好的答法应该回到项目本身。

你可以这样答：

### 版本一：强调主链路

`我觉得这个项目最核心的价值，是把一次 RPC 调用从业务入口到 provider 执行完整打通，并且把代理、调用编排、协议、传输、provider 执行这些环节拆得比较清楚。这样它不只是一个能跑的 demo，而是一套结构上比较完整的框架骨架。`

### 版本二：强调结构设计

`我觉得最核心的价值是边界拆分比较清楚，像 rpc-core、Spring 集成、Boot 自动装配、契约层和示例应用都分开了。这样后面无论是扩展使用方式，还是替换某些能力，都比把所有逻辑揉成一团要好很多。`

### 版本三：强调工程成长

`我觉得这个项目最大的价值是让我真正把一次远程调用拆成了多个明确阶段去理解，比如入口代理、调用编排、协议传输和 provider 本地执行。以前这些词我知道，但这个项目让我把它们第一次在一个完整系统里对应上了。`

这个问题最适合用来体现“你的判断”。

## 14. 如果面试官问“如果继续做，你会怎么往下演进”，怎么答

这个问题的关键不是说得多，而是说得合理。

几个比较稳的方向：

### 方向一：补强测试和可观测性

```text
如果继续做，我会优先补全更系统的单元测试和集成测试，同时增加更明确的链路日志、指标和 tracing 信息。因为对框架项目来说，能跑只是第一步，后续要可验证、可观测，排查问题才会更稳定。`
```

### 方向二：补强 provider 执行链与异常处理

```text
我会继续细化 provider 本地执行链，包括线程模型、异常分类、统一错误码和更细粒度的 provider 侧治理能力。`
```

### 方向三：补强生态和扩展能力

```text
我会继续完善 SPI 扩展点，以及更完整的注册中心、序列化器和负载均衡器扩展实现，让框架更适合做能力验证和对比实验。`
```

回答这种问题时，最好选你前面已经真正理解过的方向，不要乱开太大题目。

## 15. 一个“简历 + 面试”之间最稳的连接方式

最理想的状态是：

`简历里的项目描述，正好能自然引出你面试里的讲法。`

也就是说：

- 简历里先压缩成一段或几条 bullet
- 面试里再沿着这几个点逐步展开

例如：

### 简历里写：

```text
基于 Java 实现了一个自研 RPC 框架，围绕 consumer 代理调用、请求对象化、服务注册发现、Netty 请求响应通信和 provider 本地执行链打通远程调用闭环；在此基础上实现了 Spring / Spring Boot 集成、方法级配置、SPI 扩展，以及基础重试、限流、熔断和降级能力。`
```

### 面试里展开时就按这几个点讲：

1. 先讲 consumer 代理调用
2. 再讲请求对象化和 Netty 通信
3. 再讲 provider 本地执行链
4. 最后讲 Spring 集成和治理能力

这样你的简历和口头表达就是连着的，不会出现“简历写一套，面试讲另一套”的割裂感。

## 16. 你真正要练习的，不是答案，而是三种表达长度

为了提高稳定性，建议你把这个项目练成 3 个长度版本。

### 16.1 30 秒版

只回答：

- 项目是什么
- 最小主链路是什么

### 16.2 1 到 2 分钟版

回答：

- 项目目标
- 主链路
- 分层
- 增强能力
- 自己理解

### 16.3 5 分钟展开版

回答：

- consumer 入口
- provider 执行
- Spring 集成
- 协议与传输
- SPI 扩展
- 治理能力
- 后续演进

你如果把这三档都练出来，面试时就会非常从容。

因为无论对方给你多长时间，你都有对应版本可用。

## 17. 这篇最后想让你具备什么能力

读完这篇以后，你不只是要“知道可以怎么说”。

更重要的是，你应该开始具备这几种能力：

1. 能写出一段不空也不乱的简历项目描述
2. 能在面试开场时稳定讲清项目目标和主链路
3. 能根据追问把表达下沉到具体设计点和源码类
4. 能补上一句自己的判断，而不是只停留在复述项目内容
5. 能把前面整套文档里的理解，真正转换成对外表达能力

这才是输出阶段存在的意义。
