# 完整学习主线

## 1. 先明确：你现在不是在看文档，而是在走一条路线

很多项目文档的问题，不是内容不够，而是没有路线。

你打开一堆 Markdown 文件，会看到：
1. 这里讲一点结构
2. 那里讲一点调用链
3. 再那里讲一点配置
4. 最后又来一点面试表达

每一篇看起来都好像有价值，但组合在一起时，读者经常会有一种感觉：

`我每篇都懂一点，但整个项目还是没有真正进入脑子里。`

所以这份“完整学习主线”文档要解决的问题非常简单：

`告诉你整套课程为什么这样排，以及你每一阶段到底应该得到什么。`

## 2. 学这个项目之前，你需要先放下什么

你需要先放下一个常见误区：

`我要先把底层全懂，才能理解整个项目。`

这是错的。

正确顺序通常正好相反：

1. 先知道项目整体在做什么
2. 再知道一次调用怎么流
3. 再知道每个模块在这条调用链上的位置
4. 最后才逐步理解底层实现细节

因为底层细节本身没有问题，但如果你没有主线，它们会变成很多孤立的信息块。

## 3. 整套课程的总目标是什么

最后学完以后，你应该能够达到下面这几个层次。

### 层次一：业务层理解

你能说清楚：

`这个项目让 consumer 像本地调用一样去调用 provider 服务。`

### 层次二：主链路理解

你能说清楚：

`一次调用从业务层出发，经过代理、请求对象化、发现、路由、容错、传输，到 provider 上真正执行业务。`

### 层次三：分层理解

你能说清楚：

1. 哪些模块是示例
2. 哪些模块是框架
3. 哪些类是入口
4. 哪些类是中枢
5. 哪些类是底层支撑

### 层次四：输出理解

你能把整个项目讲给别人听，而不是只能对着源码自己看懂一点。

## 4. 为什么阶段一要从“感觉”开始

零基础读者最需要的，不是术语，而是画面。

你先要在脑子里出现这样一张画面：

```text
我在 consumer 里写 helloService.sayHello("consumer")
  -> 这并不是本地实现
  -> 底层会发一次远程请求
  -> provider 会真正执行 HelloServiceImpl.sayHello(...)
  -> 然后结果再回来
```

只要这个画面出来了，
后面你再看到：

1. `@RpcReference`
2. `RpcConsumerBootstrap`
3. `RpcProxyFactory`
4. `RpcClientInvocationExecutor`
5. `RpcRequestDispatcher`
6. `HelloServiceImpl`

这些类就不会像凭空出现，而会像这张画面上的不同站点。

## 5. 为什么阶段二要集中打主线

任何 RPC 项目，说到底都是调用链项目。

如果你不先抓调用链，后面会出现这种情况：

1. 你知道 `LoadBalancerFactory` 是干嘛的，但不知道它为什么会在那时出场
2. 你知道有 `RpcHeader`，但不知道它是在整条链哪一段真正起作用
3. 你知道有重试、限流、熔断，但不知道它们是挂在什么位置做的

主链路的价值就在这里：

`它给每一个能力安排位置。`

## 6. 为什么阶段三才去看源码

源码阅读最需要的不是“勇气”，而是“顺序”。

如果你已经通过前两阶段建立了：

1. 最小闭环
2. 一次调用的主线
3. 模块边界
4. 关键术语

那么你进入源码时，看到一个类就会自然问：

1. 这个类在主链路哪一段
2. 它是入口、编排者，还是底层执行者
3. 它解决的核心问题是什么

这时候阅读就会稳定很多。

## 7. 为什么最后一阶段要讲“输出”

因为会看和会讲是两回事。

很多人实际状态是：

1. 自己看源码时，好像能理解一点
2. 一旦让他介绍项目，就开始按技术词堆砌
3. 一旦让他回答“这个项目最核心的价值是什么”，就又说不顺

最后一阶段就是把前面建立起来的理解压缩成表达能力。
