# 仓库地图：先分清示例和框架，再谈源码

## 1. 为什么这一篇很关键

很多零基础读者第一次打开仓库时，最大的压力其实不是代码内容，而是目录结构。

当你一下看到：

```text
rpc-core
rpc-spring
rpc-spring-boot-starter
example-api
example-provider
example-consumer
```

最容易产生的反应是：

1. 这么多模块我该先看哪个
2. 哪些是业务示例，哪些是框架实现
3. 我是不是得把每个模块都马上看一遍

如果这个问题不先解决，后面阅读会非常容易散掉。

## 2. 你现在只需要先做一个最重要的区分

把整个仓库先粗暴地分成两类：

### 第一类：告诉你“这个框架怎么用”的模块

也就是：

```text
example-api
example-provider
example-consumer
```

这三个模块的价值在于：

`给你看最小闭环。`

它们不是框架本体，而是框架的使用样例。

### 第二类：告诉你“这个框架怎么做到的”的模块

也就是：

```text
rpc-core
rpc-spring
rpc-spring-boot-starter
```

这三个模块的价值在于：

`解释为什么前面的最小闭环真的能跑通。`

这个区分一定要先建立起来。

因为很多人第一次看项目时，
会把示例模块和框架模块混在一起看，
结果越看越乱。

## 3. 每个模块第一遍应该怎么理解

### `example-api`

第一遍你只要把它理解成：

`provider 和 consumer 共用的服务契约。`

它的重点不是复杂，而是“共享”。

### `example-provider`

第一遍你只要把它理解成：

`真正提供服务的一边。`

它的重点不是框架能力，而是“真实业务落点”。

### `example-consumer`

第一遍你只要把它理解成：

`真正发起调用的一边。`

它的重点是“调用入口”。

### `rpc-core`

第一遍你只要把它理解成：

`整个框架最核心的发动机。`

后面你会在这里看到：
1. 代理
2. 配置
3. 注册发现
4. 调用编排
5. 协议
6. 传输
7. 容错
8. 扩展

### `rpc-spring`

第一遍你只要把它理解成：

`把 RPC 框架接到 Spring 生命周期里的适配层。`

### `rpc-spring-boot-starter`

第一遍你只要把它理解成：

`让 Spring Boot 使用 RPC 更省事的自动装配层。`

## 4. 现在不要急着做什么

你现在不要急着：
1. 一头扎进 `rpc-core` 全部包名
2. 先研究所有配置项
3. 先研究所有扩展点
4. 先研究所有 transport 实现

你现在更重要的是先建立一句话：

`example-* 是场景和入口，rpc-* 是实现和支撑。`

只要这句话稳住了，仓库结构就不会显得杂乱无章。
